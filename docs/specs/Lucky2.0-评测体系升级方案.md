## 六、复审补充（2026-10-12 长时检验：方案是否真满足需求）

> 总判断：**方向对，评测驱动的工作流在兑现（60→100%）。但长时检验发现 2 个真 gap + 2 个治理问题**，其中 Gap 1 是产品级矛盾，不修会在演示时爆。

### 6.1 Gap 1（产品级）：数据窗口漂移 —— prompt 与库脱节

**证据链**（全部核实）：

| 事实 | 位置 |
|------|------|
| `daily_append.py`（每日开档脚本）已把库追加到 **10-09** | `app/scripts/daily_append.py` + `docs/演示题库.md`"实测已追加 10-08/10-09" |
| 最新快照日已是 **20261009**（256,011） | `eval_anta.json` notes |
| replenish 日均窗口实测 **9 天**（10-01~10-09） | `eval_anta.json` notes |
| **但 system_prompt 规则 2 仍写**："数据只覆盖 2026-10-01 ~ 2026-10-07" | `prompts/system_prompt.prompt` L46 |

**后果**：真实使用中店长问"昨天卖了多少钱"（昨天=10-09，库里有数据）→ 模型按规则 2 回答"超出数据范围" → **拒答错误**。replenish 侧更微妙：算法实际用 9 天窗口，prompt 却声明 7 天 —— 解释与事实不符。

**根因**：**prompt 的数据边界是写死的，库是活的**（daily_append 每天追加）。

**修法（推荐）**：**数据边界动态化** —— `date_info` 段从 dw 库查 `MIN/MAX(date_id)` 注入「数据可用区间」，规则 2 改为"以【今天】段给出的数据边界为准"。此后 daily_append 永不引发漂移。

**前置决策（叙事级，需项目所有者定）**：

| 叙事 | 动作 |
|------|------|
| **A. 国庆档复盘**（7 天固定） | 回滚 daily_append 的 10-08/10-09，全链回到 7 天；评测 golden 不动 |
| **B. 持续运营**（推荐 —— daily_append 的存在说明真实意图是持续运营） | 接受窗口增长 → prompt 动态边界化 + 评测集相对时间类用例补齐 + replenish 窗口语径写入文档（9 天实测值进 golden notes，已做） |

### 6.2 Gap 2：评测缺「业务有效性」层 —— SQL 100% ≠ 店长有用

现有指标全部止于 **SQL 层**（意图/工具/可执行/正确性/检索）—— **`explanation`（最终给店长看的话）没有任何评测**。

但店长要的不是数字，是**结论与行动建议**（"卖得怎么样、要不要补货"）。

**建议新增 F9 答案质量场（~8 例）**，两级判定：

| 级 | 判定 | 成本 |
|:--:|------|------|
| **规则级（首选）** | **防幻觉对账**：解释文本中的每个数字必须能在 `state["result"]` 中找到来源（纯字符串/数值匹配，零 LLM） | 0 |
| 质量级（可选） | LLM-as-judge：是否含结论/建议、是否引用正确口径 | 每例一次 judge 调用 |

> 规则级对账是**防幻觉硬约束的落地** —— 现在解释层的幻觉**完全没有检测手段**（策略原则：验证方式缺失的约束等于没有约束）。

### 6.6 S1 归因结论（2026-10-12 实测，已闭合）

**1）向量集合被重复点污染（真缺陷）**
- 现象：`metric_info_collection` **164 点**、`column_info_collection` **1060 点**。
- 根因：`MetaKnowledgeService` 用 `uuid.uuid4()` 生成 point id 且只 upsert 从不删除 → 每构建一次追加一份（8 指标 × 约 5 语义文本 ≈ 16 点/次 × 约 10 次构建 ≈ 164；字段同理）。
- 影响：`search(limit=20, threshold=0.6)` 的 20 个额度被同一实体的重复点占满 —— 实测搜「可用库存」20 个命中里只有 **1 个**不同指标、搜「销量」只有 **4 个**，期望指标被挤出 top-5，表现为"上一版能命中、这一版没命中"的回退。**字段通道同样中招**：清洗前后同一问题的不同字段数 3~6 → 12~26。

**2）召回关键词用 set 去重，顺序随进程变化（真缺陷）**
- 四处 `list(set(...))` / `set(...)`（`extract_keywords`、`recall_metric`、`recall_column`、`recall_value`）；下游按「首次命中顺序」写回 `retrieved_*`。
- 实测同一 commit 连跑 3 次：metrics recall = **1.0 / 0.0 / 1.0**，字段 MRR = 0.33 / 0.50 / 0.67。

**3）追问句的指标召回没有确定性来源（机制缺口，未修）**
- 两条失败用例的末轮问句都是纯品类/指代句：「那鞋类呢？」「只看跑鞋呢？」。实测这两句对指标集合的向量命中 **0**（阈值 0.6）——句面本身不含任何指标语义。
- 用例期望（`_tmp_probe_s1.json`）要求末轮召回「可用库存」/「销量」，只能靠 `recall_metric` 内部的 LLM 扩展词（`extend_keywords_for_metric_recall`，温度 > 0）恰好撞上。
- 规则化的「召回继承」补不上这个洞：`extract_keywords` 继承的是 `extract_conditions(上一轮)` 的值，而 `_METRICS` 取值域只有（销售额/销量/折扣率/动销率/客单价/营业额）——「可用库存」不在域内；`_GENDERS` 只有（男子/女子/儿童/男女同款）——「女款」不在域内。
- 决定性证据：两次连跑的 `extract_keywords` 输出**完全相同**（`['那鞋类呢？','鞋类']`），metrics 召回却一次 8 个、一次 0 个 → 差异只能来自 LLM 扩展词。

**对测评本身的附加判断**：这类追问句的期望**答案其实是对的**（末轮 SQL 命中 `available_qty` + `category_l1='鞋类'`，「138,602」= 鞋类占全店 256,011 的 54%），失分的是 `metrics hit@k` 这个指标 —— 它量的是"召回层有没有带出指标"，而该轮正确性实际由 `【上一轮提问】` 兜底原文保证。**因此 F2 场的通过线不能对追问句沿用 metrics hit。**

## 一、角色总览

**4 个角色，权限逐级递进（包含关系）：**

```
临时工  ⊂  普通店员  ⊂  库管  ⊂  店长
（最低）                          （最高）
```

| 角色 | 一句话定位 | 服务对象性质 | 权限层级 |
|------|-----------|-------------|---------|
| **店长** | 一家店的负责人，全权决策 | 决策者 | 最高 · 全部能力 |
| **库管 / 理货员** | 管货的人，出入库 + 补货 | 执行 + 决策 | 高 |
| **普通店员 / 导购** | 一线销售，查货卖货 | 执行者 | 中 |
| **临时工** | 旺季临时促销，快速上手 | 临时执行 | 最低 |

> **MVP 优先级**：**店长优先**（已确认）。MVP 主线 = 销售额统计 + 热卖剖析 + 门店补货 的闭环，因为店长痛点最深、决策价值最高。

## 二、角色画像

### 2.1 店长（第一用户）

| 要素 | 内容 | 来源 |
|------|------|------|
| 角色名称 | 店长（特卖店负责人） | 用户确认 |
| 身份背景 | 负责一家特卖店的人、货、场，承担销售指标与库存责任 | 用户确认 |
| 核心目标 | ① 完成销售指标 ② 少断货 ③ 少积压 | 由痛点推导 |
| 典型场景 | ① 早班开工看昨天卖了多少、哪几款最好卖<br>② **每日早晚各一次**决定向仓库补什么货、补几件<br>③ 向上汇报经营情况 | 用户确认补货节奏 |
| 典型痛点 | 数据在系统里但看不到；畅销品靠肉眼发现、滞后；补货靠经验，补多压货补少断货 | 用户原话 |
| 数字化水平 | 【待确认假设】会用手机与常用 App，能看 Excel 但不写公式，**不会 SQL** | 假设 |
| 使用频率 | 高频（每天 2-3 次） | 推断 |
| 可用能力 | **全部**：库存查询 + 出入库 + 热卖排行 + 销售额度 + 门店补货 +（仓库补货预留） | 用户确认 |

**用户故事**

```
作为【店长】，我想要【用一句话问出昨天的销售额和畅销款】，
以便【不用翻系统、不用凭记忆，就能知道经营状况并决定补货】

验收标准（Given/When/Then）：
- Given 店长已登录且昨日的销售数据已入库
  When 店长提问「昨天卖了多少、哪几款最好卖」
  Then 返回昨日销售总额与畅销款排行（含款名、销量、实付金额），
       并标明数据统计口径与时间范围
```

### 2.2 库管 / 理货员

| 要素 | 内容 | 来源 |
|------|------|------|
| 角色名称 | 库管 / 理货员 | 用户确认 |
| 身份背景 | 负责收货上架、出入库登记、盘点；**可能由店员兼任**【待确认】 | 用户确认 + 假设 |
| 核心目标 | 账实相符、货品及时上架、按建议及时补货 | 推断 |
| 典型场景 | ① 到货登记入库 ② 卖出后出库 ③ 每日盘点核对 ④ 按补货建议向仓库要货 | 用户确认 |
| 典型痛点 | 手工登记易错、核对慢、出入库记录分散 | 用户原话"依赖人工操作" |
| 数字化水平 | 【待确认假设】会用扫码枪/PDA，不写 SQL | 假设 |
| 使用频率 | 中频（每日 1-2 次） | 推断 |
| 可用能力 | 库存查询 + **出入库（写）** + 热卖排行 + 销售额度 + **门店补货** | 用户确认 |

**用户故事**

```
作为【库管】，我想要【在对话里直接登记入库/出库，并看到系统建议的补货量】，
以便【不用手工记账、不用凭经验估补货，库存与补货都有据可依】

验收标准（Given/When/Then）：
- Given 库管已登录
  When 库管提交一次入库操作（SKU + 数量 + 单号）
  Then 系统校验权限 → 二次确认 → 写入库存流水（记录经办人与时间）
       → 返回成功结果与最新库存数
- Given 同一入库单号被重复提交
  When 第二次提交发生
  Then 系统按幂等键识别为重复请求，不重复入库，并提示"该单据已入库"
```

### 2.3 普通店员 / 导购

| 要素 | 内容 | 来源 |
|------|------|------|
| 角色名称 | 普通店员 / 导购 | 用户确认 |
| 身份背景 | 一线销售，早晚班轮值 | 用户确认 |
| 核心目标 | 服务好顾客、完成个人销售 | 推断 |
| 典型场景 | ① 顾客问"这件有没有 L 码/42 码"→ **当场查库存**<br>② 顾客问"哪个卖得好"→ 查热卖排行<br>③ 卖出后做出库登记<br>④ 问"还有别的颜色吗"→ 查同款色码 | 用户确认 + 推断 |
| 典型痛点 | 查库存要跑后仓或问同事、顾客等待；不知什么好卖只能凭感觉推荐 | 推断 |
| 数字化水平 | 【待确认假设】手机 App 熟练，不看数据报表 | 假设 |
| 使用频率 | 中高频（每班多次） | 推断 |
| 可用能力 | 库存查询 + 出入库（写） + 热卖排行 + 销售额度 | 用户确认 |

**用户故事**

```
作为【普通店员】，我想要【顾客问码数时当场用一句话查到库存】，
以便【不用跑后仓、不用问同事，顾客不用等】

验收标准（Given/When/Then）：
- Given 店员已登录
  When 店员提问「某某款还有 42 码吗」
  Then 返回该 SKU 的可用库存数量与所在货位；
       若库存为 0，明确提示"已断码"并给出同款其他尺码的库存情况
```

### 2.4 临时工

| 要素 | 内容 | 来源 |
|------|------|------|
| 角色名称 | 临时工（旺季临时促销员） | 用户确认 |
| 身份背景 | 旺季/大促临时招募，**流动性高、培训时间短** | 用户确认 |
| 核心目标 | 尽快上手、能回答顾客问的码数 | 推断 |
| 典型场景 | 顾客问"有没有 42 码"→ 查库存；顾客问"哪个好卖"→ 查热卖排行 | 用户确认 |
| 典型痛点 | 不熟悉货品与系统；问同事又怕显得不专业 | 推断 |
| 数字化水平 | 【待确认假设】手机熟练，对本店业务一无所知 | 假设 |
| 使用频率 | 中频（当班期间） | 推断 |
| 可用能力 | **仅**库存查询 + 热卖排行（**看不到销售额度**，**不能出入库**） | 用户确认 |
| 权限最小化理由 | 流动大、不熟悉 → 给最小可用权限，防止误操作与经营数据外泄 | 设计意图 |

**用户故事**

```
作为【临时工】，我想要【快速查到有没有某个尺码、哪个款卖得好】，
以便【能独立应对顾客提问，不必反复求助老员工】

验收标准（Given/When/Then）：
- Given 临时工已登录（最小权限）
  When 临时工尝试查询销售额度
  Then 系统拒绝并提示"当前账号无此权限，请联系店长"
```

## 三、权限矩阵（能力 × 角色）

**唯一定稿版**（后续 FR 与测试用例以此为准）：

| 能力 / 子功能 | 临时工 | 普通店员 | 库管 | 店长 |
|--------------|:-----:|:-------:|:----:|:----:|
| 库存查询（读） | ✅ | ✅ | ✅ | ✅ |
| **出入库（写）** | ❌ | ✅ | ✅ | ✅ |
| 热卖排行 | ✅ | ✅ | ✅ | ✅ |
| 销售额度统计 | ❌ | ✅ | ✅ | ✅ |
| 门店补货建议 | ❌ | ❌ | ✅ | ✅ |
| 仓库补货建议（预留） | ❌ | ❌ | ❌ | ✅ |

### 3.1 关键设计结论：能力 ≠ 权限

**`dataquery` 能力内部需要再分权限** —— 热卖排行对全员开放，销售额度对临时工关闭。

这意味着权限控制**不能只挂在"能力"这一层**，必须下沉到**子功能粒度**。落地时每个子功能需带权限标记，路由/执行层按当前登录角色校验。

### 3.2 角色能力的增量关系

| 角色 | 相对上一级新增 |
|------|--------------|
| 临时工 | 库存查询（读）+ 热卖排行 |
| 普通店员 | + 出入库（写）+ 销售额度 |
| 库管 | + 门店补货建议 |
| 店长 | + 仓库补货建议（预留） |

## 四、身份识别与登录

### 4.1 登录方式（已确认）

**账号密码 / 工号 PIN 登录。**

| 项 | 设计 |
|----|------|
| 凭证形式 | 工号 + 密码（或 PIN） |
| 登录后行为 | 自动带出「经办人」身份，出入库等写操作**无需手填经办人** |
| 会话保持 | 【待确认】建议单次会话有效，超时自动退出 |
| 错误处理 | 【待确认】连续错误次数上限与锁定策略 |

### 4.2 为什么必须登录（而不是可选的）

因为 **Agent 现在具备写操作能力**（出入库）。写操作必须能回答两个问题：

1. **谁干的** → 操作审计（经办人留痕）
2. **他有没有资格干** → 权限校验

没有登录，这两件事都无法成立。

### 4.3 账号生命周期

临时工流动性高，账号的"开通 → 使用 → 回收"需要明确规则。

**已确认结论（完整规则见 5.7）**：

- 账号由**店长创建**，开通时记录 `created_by`；
- 临时工账号**绑定用工周期**（`valid_from` / `valid_to`），**到期自动失效**，无需人工干预；
- 正式员工账号长期有效，离职时手动置为停用并记录 `leave_date`。

## 五、员工数据结构（dim_staff）

### 5.1 员工的三重身份

字段设计由员工承担的三重身份决定：

| 身份 | 作用 | 对应字段 |
|------|------|---------|
| **登录主体** | 证明"你是谁" | `staff_id` + `credential_hash` |
| **经办人** | 记录"谁干的"（被 `fact_inventory_flow` 引用） | `staff_id` |
| **权限载体** | 决定"能看什么、能做什么" | `role_codes` → 权限点 |

### 5.2 结构方案选型

| 方案 | 结构 | 复杂度 | 灵活性 | 结论 |
|------|------|:------:|:------:|------|
| **A. 单表 + 角色码** | 1 张员工表，角色存码值 | 低 | 中 | ✅ **采用** |
| B. 标准 RBAC | 员工 / 角色 / 权限 三表 + 2 张关联表 | 高 | 高 | 单店场景属过度设计 |
| C. 单表 + 权限内嵌 | 员工表直接存权限清单 | 低 | 高 | 一人一配，易配错、难排查 |

**采用方案 A**，与整体"参数化、改配置不改代码"的思路一致。

### 5.3 表结构

| 字段 | 类型 | 必填 | 口径说明 |
|------|------|:----:|---------|
| `staff_id` | 字符串(20) | ✅ | **工号，主键**，兼登录名 |
| `name` | 字符串(30) | ✅ | 姓名（展示建议用"王店长"式称谓） |
| `role_codes` | 字符串(50) | ✅ | **角色码，多值**（逗号分隔），如 `STAFF,KEEPER` |
| `credential_hash` | 字符串(128) | ✅ | 凭据**加盐哈希**（⚠️ 严禁明文） |
| `status` | 枚举 | ✅ | 启用 / 停用 |
| `valid_from` | 日期 | — | 账号生效日（临时工必填） |
| `valid_to` | 日期 | — | 账号失效日；空 = 长期有效 |
| `hire_date` | 日期 | — | 入职日期 |
| `leave_date` | 日期 | — | 离职日期 |
| `created_by` | 字符串(20) | — | 账号开通人工号（留痕） |
| `created_at` / `updated_at` | 时间 | ✅ | 审计字段 |

### 5.4 角色码与权限点

**角色码（4 个）→ 权限点集合：**

| 角色码 | 角色 | 权限点集合 |
|--------|------|-----------|
| `MANAGER` | 店长 | `inventory.read` · `inventory.write` · `dataquery.hot` · `dataquery.sales` · `replenish.store` · `replenish.warehouse`（预留） |
| `KEEPER` | 库管 | `inventory.read` · `inventory.write` · `dataquery.hot` · `dataquery.sales` · `replenish.store` |
| `STAFF` | 普通店员 | `inventory.read` · `inventory.write` · `dataquery.hot` · `dataquery.sales` |
| `TEMP` | 临时工 | `inventory.read` · `dataquery.hot` |

**权限点定义（6 个，下沉到子功能粒度 —— 落实"能力 ≠ 权限"）：**

| 权限点 | 覆盖的子功能 |
|--------|-------------|
| `inventory.read` | 库存详情、出入库记录查询、库存预警、断码查询 |
| `inventory.write` | 出入库登记（**写操作**） |
| `dataquery.hot` | 热卖排行 |
| `dataquery.sales` | 销售额度统计 |
| `replenish.store` | 门店补货建议 |
| `replenish.warehouse` | 仓库补货建议（预留） |

### 5.5 角色叠加的表达（已确认）

**业务规则**：库管职责可与店员**叠加**（一人兼任），其余角色保持单一。

**数据表达**：`role_codes` 采用**多值字段** —— 店员兼库管存为 `STAFF,KEEPER`。

**权限计算**：取集合内各角色权限的**并集**。

> **说明**：因 `KEEPER` 的权限已包含 `STAFF` 全部权限，叠加后的实际结果与单角色 `KEEPER` 相同。保留多值设计是为将来新增其他独立叠加项（如"培训员"）时**无需改表结构**。

### 5.6 权限映射的存放位置（已确认）

**存在配置文件，不建数据库表。** 形态示例：

```yaml
roles:
  MANAGER:
    name: 店长
    permissions: [inventory.read, inventory.write, dataquery.hot,
                  dataquery.sales, replenish.store, replenish.warehouse]
  KEEPER:
    name: 库管
    permissions: [inventory.read, inventory.write, dataquery.hot,
                  dataquery.sales, replenish.store]
  STAFF:
    name: 普通店员
    permissions: [inventory.read, inventory.write, dataquery.hot, dataquery.sales]
  TEMP:
    name: 临时工
    permissions: [inventory.read, dataquery.hot]
```

改权限**只改此文件**，不动表结构、不动代码。

### 5.7 账号生命周期（已确认）

| 环节 | 规则 |
|------|------|
| 开通 | 由店长创建，记录 `created_by` |
| 有效期 | 临时工**必填** `valid_from` / `valid_to`（绑定用工周期）；正式员工可留空（长期有效） |
| 登录校验 | `status = 启用` **且** 当前日期 ∈ [`valid_from`, `valid_to`] 方可登录 |
| 到期回收 | **到期自动失效**，无需人工干预 |
| 提前离职 | 手动置 `status = 停用`，并填 `leave_date` |

### 5.8 红线

- `credential_hash` **严禁明文存储**，必须加盐哈希。
- 若增加手机号等联系方式字段，属个人信息，须脱敏处理；**建议单店版不存**。

| `T005` | 徐婷 | `TEMP` | **有效期已过** | 用工周期 2026-08-01 ~ 08-31，已过期 | 启用（登录仍应被拒） |

> **`T005` 的设计意图**：`status` 仍为"启用"，但**有效期已过** → 登录时应被拒。
> 这条数据用于验证「有效期校验」是**独立于**「状态校验」的第二个关卡 —— 只看 `status` 会漏掉过期账号。

## 六、出入库写操作的安全设计（完整版）

**已确认采用完整版安全等级。** 库存即资产，写操作需五重保护：

| # | 措施 | 要解决的问题 | 具体做法 |
|---|------|-------------|---------|
| 1 | **幂等键** | 网络抖动/重复点击导致库存虚增 | 幂等键 = `单据号 + SKU + 操作类型`；重复提交返回首次结果，不重复入库 |
| 2 | **二次确认** | 误操作（数量多打一个零） | 提交前弹出确认摘要（SKU / 数量 / 操作类型 / 经办人），确认后才执行 |
| 3 | **操作留痕** | 出了问题查不到人 | 每次写入 `fact_inventory_flow`，记录：经办人、时间、类型、SKU、数量、单号 |
| 4 | **权限校验** | 越权操作 | 执行前校验当前角色是否具备该操作权限（临时工无出入库权限） |
| 5 | **流水可核对** | 账实不符时无法追溯 | 库存流水与库存快照可相互核对，支持按单据号追溯全过程 |

### 6.1 异常边界清单（出入库专项）

| 边界情况 | 期望行为 |
|---------|---------|
| 重复提交同一单据 | 幂等拦截，提示"该单据已处理"，不重复记账 |
| 出库数量 > 现有库存 | 拒绝执行，提示当前可用库存，**不允许负库存** |
| 入库数量为 0 或负数 | 拒绝执行，提示"数量必须为正整数" |
| 无权限角色尝试操作 | 拒绝并提示联系店长 |
| 提交过程中断网 | 【待确认】提示重试；重试时靠幂等键防重复 |
| SKU 不存在或已下架 | 拒绝执行，提示核对商品信息 |

## 七、双通道并存（Agent + 固定页面）

**已确认：Agent 与固定页面双通道并存。**

| 通道 | 定位 | 适合的操作 |
|------|------|-----------|
| **Agent（对话）** | 便捷、口语化、随身可用 | 日常出入库、查库存、查热卖、看补货建议 |
| **固定页面** | 正式、结构化、适合批量 | 盘点、调拨、报损等重操作【待确认具体范围】 |

### 7.1 新增的一致性要求（重要）

两条通道都能写库存，就必须保证**数据一致**：

| 要求 | 说明 |
|------|------|
| 同源写入 | 两个通道必须写同一份库存流水表，不允许各写各的 |
| 幂等共用 | 幂等键在两个通道间**共用**——页面入过库的单据，Agent 再提交也要被拦住 |
| 库存实时 | 任一通道写入后，另一通道读取到的库存必须是最新值 |
| 留痕一致 | 无论走哪个通道，经办人与时间都要记录 |

> **风险提示**：双通道是数据一致性风险的来源。如果排期紧张，建议一期先以 **Agent 为主通道**、固定页面仅保留只读查询，待出入库稳定后再开放页面的写入能力。

## 八、一天中的使用节奏（场景地图）

把四个角色放回真实的一天，能看清每个能力在什么时候被用到：

| 时间 | 角色 | 场景 | 用到能力 |
|------|------|------|---------|
| 08:30 | 店长 | 开工前看昨天卖了多少钱、哪几款好卖 | 销售额度 + 热卖排行 |
| 08:45 | 库管 | 按系统建议的补货量向仓库要货 | 门店补货 |
| 09:00 | 店家/库管 | 收到货后登记入库 | 出入库（写） |
| 10:00-20:00 | 店员 / 临时工 | 顾客问码数 → 当场查库存；问哪个好卖 → 查热卖 | 库存查询 + 热卖排行 |
| 卖出后 | 店员 | 出库登记 | 出入库（写） |
| 21:00 | 店长 | 看当日销售、决定是否二次补货 | 销售额度 + 门店补货 |
| 闭店后 | 库管 | 盘点核对 | 库存查询 +（固定页面盘点） |

> **观察**：**补货发生在早晚两次**（08:45 / 21:00），与店长的两个使用高峰完全重合 —— 这印证了"补货建议"和"销售额度"应该做在同一轮对话里，而不是拆成两个工具。

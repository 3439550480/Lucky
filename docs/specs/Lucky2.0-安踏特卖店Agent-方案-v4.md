## 一句话定位

Lucky 是一个面向安踏品牌特卖门店的**商品销售数据智能体**——让门店员工不必依赖肉眼与经验，用自然语言即可完成销售额统计、商品热卖剖析、补货建议与库存查询。

上一版我推测的矛盾是"折扣与断码的博弈"，**方向错了**。你给出的真实矛盾是：

| # | 痛点 | 说明 |

> 让一个不懂 SQL、看不到数据库的特卖店员工，用大白话问出"上周哪几款卖得最好、还剩多少、该补多少"，得到可直接执行的答案。

## 三、折扣规则完整算法（本轮核心新增）

### 3.1 基准折扣（按商品上市时间距售出时间）

| 商品账龄 | 基准折扣 | 折扣率（售价/吊牌价） | 示例 |
|---------|---------|---------------------|------|
| 1.5 年以上老款 | **2 折** | 20% | 2024-01 上市，2026-03 售出 → 2 折 |
| 1 年以上老款 | **3.5 折** | 35% | 2024-10 上市，2026-03 售出 → 3.5 折 |
| 半年以上款式 | **5 折** | 50% | 2025-08 上市，2026-03 售出 → 5 折 |
| 最近半年新款 | **7 折** | 70% | 2026-01 上市，2026-03 售出 → 7 折 |

### 3.2 满件门槛规则（已修正：按缺口件数递增）

```
整单件数 = 该订单所有商品数量之和（按整单总件数判定）

若 整单件数 ≥ 4：每件按各自基准折扣结算
若 整单件数 < 4：加折幅度 = 缺口件数 × 10%
                 （缺口件数 = 4 − 整单件数）

每件最终折扣率 = 基准折扣率 + 加折幅度，上限 10 折（原价封顶）
```

**加折对照表**

| 整单件数 | 缺口件数 | 加折幅度 | 2 折商品实付 | 5 折商品实付 | 7 折商品实付 |
|---------|---------|---------|-------------|-------------|-------------|
| ≥ 4 件 | 0 | 0% | 2 折 | 5 折 | 7 折 |
| 3 件 | 少 1 件 | **+10%** | 3 折 | 6 折 | 8 折 |
| 2 件 | 少 2 件 | **+20%** | 4 折 | 7 折 | 9 折 |
| 1 件 | 少 3 件 | **+30%** | 5 折 | 8 折 | **10 折** |

**示例（你给的两个场景，均已对齐）**

- 顾客买 3 件，其中含一件 2 折老款 → 缺 1 件 → 加折 10% → 该件按 **3 折**（20%+10%）结算。
- 顾客买 1 件 7 折新款 → 缺 3 件 → 加折 30% → 按 **10 折**（70%+30%）结算，正好触及封顶。
- 若买满 4 件 → 全部按基准折扣（2 折商品就是 2 折）。

> **边界说明：** 封顶 10 折（原价）只在 7 折商品买 1 件时才会真正触及（70%+30%=100%）；其余组合加折后仍低于原价，规则自洽。

### 3.3 为什么这个规则很关键（技术难点）

**这是"跨行依赖"订单规则，不能按行简单累加。**

单件实付 = 吊牌价 × 折扣率，而折扣率依赖**整单总件数**这一订单级属性。这意味着正确的 SQL 必须先聚合订单件数、再回连每一行：

```sql
SELECT ...,
       吊牌价 * LEAST(1.0,
           基准折扣
           + CASE WHEN SUM(qty) OVER (PARTITION BY order_id) < 4
                  THEN (4 - SUM(qty) OVER (PARTITION BY order_id)) * 0.1
                  ELSE 0 END
       ) AS 实付
FROM fact_sales ...
```

**这同时是最佳演示点与技术亮点。** 绝大多数 Text2SQL demo 只会 `SUM(amount)`；而你的 Agent 要答对"上周销售额"，必须正确处理整单促销（且是**按缺口件数递增**的加折，比固定一档更难）。这体现了三件事：① 业务规则真实；② SQL 生成有难度梯度；③ 可以用"同一问题 Agent 答对 vs 朴素 SQL 答错"做对比演示，说服力极强。**建议把这个规则作为演示题库的头号种子题。**

**设计取舍：**

- **方案甲（推荐）**：事实表存"吊牌价 + 基准折扣 + 实付金额"，整单促销在**生成数据时就算好**，SQL 只需正确聚合；
- **方案乙**：只存吊牌价与折扣率，所有计算交给 SQL 现算。

建议甲为主（保证数据自洽可核对），但**保留一道需要窗口函数的演示题**，让 Agent 展示对此规则的理解。

### 3.4 商品主数据与货号规则（已定稿）

`dim_product` 主键为 **8 位货号**，前 5 位承载业务语义（你的规则），后 3 位保证全局唯一：

```
位 1    尺码容别   1 = 大码   2 = 小码   3 = 儿童码
位 2    男女       0 = 男女同款   奇数 = 男装   偶数 = 女装
位 3-4  生产年份   24 / 25 / 26
位 5    生产季度   1 = 春   2 = 夏   3 = 秋   4 = 冬
位 6-7  品类序号   01~99，同组合内去重
位 8    校验位     前 7 位加权和 mod 10
```

**折扣档位直接由年份位判定**（取代原"上市日期"字段）：24 → 2 折；25 → 3.5 折；26 非夏 → 5 折；26 夏 → 7 折。

## 五、四个功能的落地（单店版）

### ① 销售额度统计（能力：dataquery）

| 项 | 设计 |
|----|------|
| 支持问法 | "今天卖了多少" "上周销售额" "这周比上周怎么样" "哪个品类卖得好" "会员买的占比多少" |
| 关键口径 | **实收销售额** = Σ 实付金额（含满件折扣结果）<br>**吊牌销售额** = Σ 吊牌价 × 数量<br>**整体折扣率** = 实收 ÷ 吊牌（加权，非平均）<br>**平均单价** = 实收 ÷ 件数<br>**单量** = 订单号去重<br>**连带率** = 总件数 ÷ 单量 |
| 亮点指标 | **连带率**（特卖店核心指标，反映"满 4 件"政策的撬动效果）——平均一单买几件，直接关联折扣规则 |
| 验收 | GWT：给定一批含满件折扣的订单，问"上周销售额" → 返回实收/吊牌/折扣率/单量/连带率，且与手工 SQL 逐项一致；特别地，**能正确识别不足 4 件订单已加折** |

### ② 商品热卖程度剖析（能力：dataquery）

| 项 | 设计 |
|----|------|
| 支持问法 | "哪些款卖得最好" "XX品类销量排行" "哪个系列最受欢迎" "哪些款要清仓" "畅销款还剩货吗" |
| 热卖分析 | **四象限**（销量 × 折扣深度）：爆款 / 促销走量款 / 潜力款 / 滞销款<br>辅助：售罄率、断码率、日均销量、连带率贡献 |
| 多维切片 | 可按品类 / 特卖属性 / 性别 / 系列 / 季节任一维度透视（D7 三维度全部可用） |
| 验收 | GWT：问"上周热卖排行" → 返回按四象限标注的排行，每类至少 1 例可核验；可按特卖属性切片（如"过季商品里哪些卖得好"） |

**四象限定义（销量 × 折扣深度）**

| 象限 | 销量 | 折扣 | 含义 |
|------|------|------|------|
| **爆款** | 高 | 浅（折扣小） | 不打折也畅销 |
| **促销走量款** | 高 | 深（折扣大） | 靠打折冲量 |
| **潜力款** | 低 | 浅 | 卖得少但不打折，可能缺货/陈列问题 |
| **滞销款** | 低 | 深 | 打折也卖不动，需清仓 |

### ③ 补货建议（能力：replenish）

> **补货口径（D13）：门店每日早晨与晚上各补一次货**（向仓库进货，仓库充足），不是给仓库补货。

```
建议补货量 = max(0, 日均销量 × 目标覆盖天数 − 现有库存 − 在途库存)
若 现有库存 + 在途 < 安全库存（= 日均销量 × 安全天数）→ 触发告警
按最小起订量（MOQ）向上取整 ｜ 仓库充足，只补门店
```

| 参数 | 默认值（按品类可配，写入 dim_replenish_policy） |
|------|-----------------------------------------------|
| 日均销量 | 近 N 天均值，N = max(提前期×2, 7)（数据窗口仅 7 天时按窗口内日均估算） |
| 目标覆盖天数 | 鞋 21 天 / 服 14 天 / 配件 30 天（示例值，待你确认） |
| 安全天数 | 7 天 |
| **补货频次** | **每日 2 次（早班 / 晚班）**，补货量按"覆盖至下次补货"的间隔折算 |
| 分级输出 | 紧急补货 / 建议补货 / 库存充足 |

> **约束：** 补货计算**禁止生成 SQL**，由固化 Python 算法执行（可单测）；LLM 仅解释"为什么这样建议"并引用计算明细。参数改配置不改代码。

验收（GWT）：某 SKU 日均销量 10 件、现有库存 20、在途 0、覆盖 14 天 → 建议补 120 件、等级"建议补货"、附计算明细与参数来源。

### ④ 库存查询（能力：inventory）

| 库存详情 | 按 SKU / 品类 / 系列查当前库存、可用库存 |
| 入库查询 | 按时间/单号查入库记录（采购入库/退货入库） |

## 七、补货算法与参数（已定稿）

### 7.1 门店补货公式（本期实现）

```
建议补货量 = max(0, 日均销量 × 覆盖天数 + 日均销量 × 安全天数 − 现有库存 − 在途库存)
```

- **不设 MOQ**：算出有缺口即补，缺口几件补几件（门店向仓库要货属内部调拨，无起订量约束）
- **不取整**：直接输出件数
- **执行节奏**：每日早、晚各跑一次
- **日均销量口径**：窗口内该款日均（国庆 7 天窗口），不引入影子历史数据

### 7.2 参数表

| 参数 | 鞋 | 服 | 配件 | 来源 |
|------|-----|-----|------|------|
| 覆盖天数 | **7 天** | **3 天** | **14 天** | 用户真实业务值 |
| 安全天数 | **3 天**（全品类统一） | | | 用户真实业务值 |
| MOQ | 不适用（门店补货不设） | | | 用户决策 D14 |

> 参数落在 `dim_replenish_policy` 表中，可按品类配置、随时调整，不改代码。

### 7.3 仓库补货参数（预留，本期不实现）

| 参数 | 鞋 | 服 | 配件 |
|------|-----|-----|------|
| MOQ | 20 件 | 30 件 | 20 件 |

> 仓库补货作为第 4 个能力（`warehouse_replenish`）与前三能力平级预留，MOQ 语义挂在此处（向供应商采购的起订量）。
